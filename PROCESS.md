# Process overview

MoveOut coordinates free student move-out handovers. This account covers the project through Crit 10: selection, agent direction, implementation, corrections and current evidence. It was written with agent assistance; the instructions and choices described are mine, and the verification below was executed by agents, not through a documented personal or classroom trial unless stated otherwise.

## Choosing the problem, the stack, and a database bug (Crits 7-8)

Student move-out handovers gave an earlier, vaguer idea (shared-fridge coordination) a deadline and an observable outcome: whether someone actually collected an item, not just expressed interest. The brief limited MoveOut to free collection, pickup windows, one confirmed recipient per item, cancellation and completed handovers, with exact addresses hidden from unconfirmed recipients ([ab091d7](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/ab091d7c22f21d30ab02b9fca04817a2d30bdc6a), routes/views in [3929ad3](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/3929ad341d07ca188ce4e020037e911150f693de)). ANU's [Give It Forward project](https://mccuskerinstitute.anu.edu.au/project/give-it-forward-circular-giving-in-residential-halls/) grounds the problem without proving scheduling causes the waste; [Robin Sloan](https://www.robinsloan.com/notes/home-cooked-app/) and [Aurora Harley](https://www.nngroup.com/articles/visibility-system-status/) argue for small-group scope and clear status feedback. README states the resulting promises; CLAUDE.md states the rules they depend on; tests protect the invariants.

Node 24 + Hono + SQLite ([9cda16a](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/9cda16a3293dbdca1ff3136df34d8ee65a4c18f0)) needs no separate database service and serves forms that work without JavaScript, at the cost of synchronous database work, cookie-only identity with no recovery, and a single-process transport. My workflow separates implementation from review: Claude makes the change, Codex checks it against the brief's actual behaviour, I feed findings back as concrete fixes. One early fix ([491a012](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/491a0129fbbdb9388df6a8f60d851576731f3c97)) gave MoveOut its own database filename after the persisted Fridge Rescue schema, on the same Fly volume, conflicted with the new model.

## The multiplayer decision and its bugs (Crit 9)

Crit 9 added updates that preserve a person's unfinished form when someone else changes shared state, without letting them keep seeing a now-unavailable item as open. [ADR 002](docs/decisions/002-live-updates-preserve-input.md) compares full refresh, delayed sync, and updating state while preserving input; the implementation ([a0f969a](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/a0f969a)) uses SSE to signal a change with no business data on the wire — every viewer re-fetches through its existing permission checks.

Review found four browser bugs (stolen focus, withdrawn items keeping usable forms, protected cards missing addresses, empty-to-nonempty sections not appearing) and one real database bug: confirming an already-cancelled application could reserve the item before the application update was found to have changed nothing, because only one of two guarded updates was checked before committing. The fix throws inside the transaction the moment either guarded `UPDATE` reports zero rows changed, so the rollback undoes both ([ceb556a](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/ceb556a), regression test in `spec/moveout.test.ts`). The browser script itself needed its own review pass (zoned vs. UTC times, a file-input assertion on a form with none, `networkidle` waits on a page with a permanent SSE connection, force-clicking a disabled button) before its passes meant anything ([be44efe](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/be44efe)).

## Crit 10: multi-user verification, server-side logging, and a URL-only entry point

This crit rehearses the final project's core multi-user claim: two classmates, each in their own Chrome profile with no shared cookies, use the app from its URL alone while I narrate from server logs who did what, without touching the UI myself.

I had Codex re-verify the existing identity and permission model before changing anything. That confirmed the device-cookie identity (`src/session.ts`), the creator/claimant checks already on every write route, address privacy and the state-transition guards — all server-side, all still passing — but found three real gaps: no business-event logging existed (only a startup line), `reflections/crit-10.md` didn't exist, and `/readme/` had no link back into the app, so a visitor arriving there from a shared link had no way in but editing the URL by hand — a direct conflict with "enter from the URL alone."

The main addition is `src/log.ts` ([ADR 003](docs/decisions/003-business-logging.md)): one JSON line per real action to stdout, read live with `mise exec -- flyctl logs -a comp4020-final-tavewang`. Each line resolves its actor from the server-trusted device id, never a client-supplied value, and hashes it before writing — the cookie is a credential (`CLAUDE.md`), so logging it plainly would let anyone reading Fly's logs replay it as that visitor. The hash is deterministic per device, so one visitor's actions correlate, and not practically invertible back to the cookie. Outcomes split into `success` (only once the write actually committed), `denied` (ownership check failed), `invalid` (validation/precondition failed), `conflict` (lost a race or hit an already-settled row), and `error` — so a rejected write is never recorded as success, and a genuine fault isn't mislabelled a business conflict. An `affected` field, set only when it differs from the actor, lets a line say "the mover confirmed Bob's request," the exact distinction this crit's narration needs.

I had Claude wire this into every existing write route, covering the denial/conflict path at each site, not just success — a log that only records success can't help diagnose a rejected action, which is exactly what this brief tests for. New tests (`spec/log.test.ts`) run the real server as its own process and read its actual stdout rather than mocking the logger, since a mock only proves the function is called: two devices get different, stable actor ids; a successful confirm correlates to the right resources and distinguishes actor from affected; a denied cancel never appears as success; no line contains a cookie, address, nickname or note.

Codex's audit also flagged a test whose name claimed more than its body checked — "a non-creator can't ... confirm its applications" never actually called `/confirm`. I extended it, and added tests for creator-only write routes, blocking someone else's timeslot change, same-nickname device isolation, and address visibility surviving a rejected confirmation attempt. No permission bug turned up in the existing routes — the gap was in test coverage, which CLAUDE.md's new logging section now documents alongside the identity rules it builds on.

The home page gained a short plain-language explanation of the two roles and a statement that the browser, not an account, holds identity — a UI gap, not a permission one, since the server check never depended on the user understanding this.

## Current verification and remaining work

As of this write-up: `pnpm typecheck`, `pnpm test` (23 tests, up from 15) and the new business-log integration tests all pass against a disposable `DATA_DIR`. `pnpm check:evidence` now separately requires `reflections/crit-10.md` to exist and be non-empty, rather than accepting any of the three crits' reflections as proof this week's is done. `scripts/browser-verify.mjs` (Crit 9's Playwright script) has not been re-run this crit — it doesn't yet assert anything about the new logging output, and the actual two-classmate, separate-Chrome-profile demo required by the brief has not happened at the time of writing; both remain open before the crit itself. Deployment (`flyctl deploy`) and a live-log check against the deployed app are also not yet done. No user trial or measured reduction in waste is claimed.
