# Process overview

MoveOut helps students discover free items and arrange collection before a moving deadline. This account covers the pickup upgrade in [beb41e7](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/beb41e7ee8f8f433c60edf323f05bb6d204df367), a following round's accounts feature, and three rounds of bugs that feature introduced, fixed on 5–7 November 2026. Prepared with AI assistance from my instructions, project history and recorded checks. Automated and agent-executed verification is distinguished from personal or classroom use; no user trial is claimed.

## Choosing a problem and defining good

I explored project ideas with ChatGPT, including shared-fridge coordination, but kept asking whether they solved a real problem. Student move-outs supplied a deadline and an observable outcome: an item actually collected. The pivot from Fridge Rescue is in [ab091d7](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/ab091d7c22f21d30ab02b9fca04817a2d30bdc6a). The brief separated interest from confirmation, required one confirmed recipient, and excluded payments, delivery and chat — boundaries that gave Claude specific behaviours to implement.

ANU's [Give It Forward project](https://mccuskerinstitute.anu.edu.au/project/give-it-forward-circular-giving-in-residential-halls/) established a local waste problem, not evidence that scheduling causes it. [Sloan's small-group software argument](https://www.robinsloan.com/notes/home-cooked-app/) and [Harley's status-visibility guidance](https://www.nngroup.com/articles/visibility-system-status/) were added during documentation review, after the initial implementation — articulating the rationale, not retrospectively proving the design worked. README defines good as clear, reliable handovers; CLAUDE.md translates that into rules, and the specs check selected promises. Usefulness still needs human evaluation.

## Stack and agent workflow

The Node, Hono and SQLite scaffold in [9cda16a](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/9cda16a3293dbdca1ff3136df34d8ee65a4c18f0) survived the pivot. Node's built-in SQLite avoided another database service; server-rendered forms kept basic actions usable without JavaScript. This fits the course's one-machine deployment, with records and photos under DATA_DIR — at the cost of synchronous database work, owning migrations, and a live-update design that would need reconsideration across multiple servers. Browser-cookie identity reduces setup but has no account recovery.

My workflow became implementation followed by review: Claude built changes, Codex examined them against the brief, and I returned concrete findings for correction. The review criteria needed to describe what a person should see and do, including rejection and cancellation, rather than merely whether a route returned success. For pickup coordination and accounts, the brief specified two separate browsers and genuinely independent devices as acceptance criteria — already a repository pattern from [be44efe](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/be44efe). This costs review time and can still share a wrong assumption across agents; its value depends on producing inspectable behaviour and regression checks, not reassuring completion messages.

## Corrections that changed the harness

Persistence first exposed an assumption during the pivot: the surviving Fridge Rescue database had an incompatible items table. [491a012](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/491a0129fbbdb9388df6a8f60d851576731f3c97) moved MoveOut to a separate database filename without deleting the old file. Later changes use additive migrations and tests against an older schema — the pattern this round's accounts migration also follows.

Crit 9 added SSE updates in [a0f969a](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/a0f969a); [ADR 002](docs/decisions/002-live-updates-preserve-input.md) chooses prompt shared-state updates with protected drafts over full-page reloads. Review found that confirming an already-cancelled application could reserve the item without a valid recipient; guarded updates with rollback became an explicit rule.

Crit 10 added business-action logging; [ADR 003](docs/decisions/003-business-logging.md) explains hashed actor identifiers: nicknames cannot distinguish people reliably, raw cookies would expose credentials.

## Final iterations: discovery and pickup coordination

The public Browse pool widened the original link-only scope. [ADR 004](docs/decisions/004-public-browse-visibility.md) records an explicit Public/Unlisted choice, enforced in the database query; pre-existing pages migrate to unlisted, protecting earlier expectations instead of silently publishing them.

I next asked for practical improvements to collection. The pickup upgrade supplies the missing confirmed time, claimant-controlled travel status, and a reschedule requiring the other party's agreement; before acceptance, the original appointment remains binding. Email was considered and deferred because no external service was configured.

The [pickup implementation](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/beb41e7ee8f8f433c60edf323f05bb6d204df367) includes migration, permission and concurrency tests, and harness rules. A two-browser check caught a draft erased by live updates; the fix protected the whole pickup card while any part was being edited — too coarse, since it also froze shared facts and any incoming reschedule proposal unrelated to the open draft. Static review also flagged an empty reschedule selector when only the current timeslot exists.

## Fixing the two pickup-card bugs

Both were reproduced against a locally running server with two Playwright contexts before being fixed, not patched from the code alone. The reschedule-draft bug traced to `syncPickupCard` checking `isProtected()` on the whole `.pickup-card`. Fixed by splitting the card into `[data-pickup-facts]` (always refreshed) and `[data-reschedule-area]` (skipped only when its own form holds a draft, then marked with a visible "this changed while editing" note rather than silently dropping the update). A related gap: cancelling while a draft was open left departure-status and reschedule buttons enabled, since the staleness pass predated those forms. The empty-selector bug was an ordering mistake — the valid-slot count was checked before excluding the current slot. Both are covered by a new automated test and a saved browser script (`scripts/browser-verify-pickup-card.mjs`, 16 checks).

## Adding accounts without breaking anonymous identity

The brief asked for register/login/logout, linking a browser's existing anonymous pages and requests to an account, reaching that data from a different device, and cross-account isolation — layered on the device-cookie identity, not replacing it. `accounts` (email, scrypt-hashed password) and `account_sessions` (a server-revocable row; the cookie carries only its id) are new tables; `moveouts.creator_account_id` / `applications.claimer_account_id` are nullable, additive columns set only by a claim pass on register/login, matching the signing-in device's own existing rows and never a row another account already claimed. Every ownership check (`isCreator`, `isClaimant`) now matches on device id **or** signed-in account id.

Browser-level testing (`scripts/browser-verify-accounts.mjs`) found a real gap code review missed: the write-side checks were correctly widened, so a second device signed into the right account could already POST a departure-status change, but `GET /m/:id`'s "Your requests" query was separate hand-written SQL that only matched `claimer_device_id` — so that device could act on a request it could never see listed through the UI. Fixed by widening that read query the same way, covered by both an HTTP test and the browser script that caught it.

A second, unrelated bug surfaced while writing the accounts test: `spec/helpers.ts`'s cookie jar read `Set-Cookie` with `Headers#get`, which comma-joins multiple same-named headers into one invalid string — invisible while every route only ever set one cookie, but register/login set two (`device` and `session`) in the same response. Fixed with `Headers#getSetCookie()`, Node's array-returning form.

## A real vulnerability: logout didn't revoke device-based access

Local testing (reproduced with Codex, against a running server with two independent browsers) found that the accounts round's "widen" rule — `isCreator`/`isClaimant` matching on device id **or** signed-in account id — had an unintended consequence: once a page or application was linked to an account, the original device cookie that created it kept working as an alternative credential forever, including after the account's session was logged out. Browser A could create a page, register, log out, and still reach and manage that page through its own unrevoked device cookie — logout only deletes the session row, and nothing about it touches the separate device cookie.

The fix (`src/ownership.ts#matchesOwner`) replaces the OR with a one-way transition: once an entity's `*_account_id` is non-null, device id stops counting entirely — only a live session for that exact account is a valid credential. Until something is claimed, device id is still the only identity, preserving every pre-accounts behaviour unchanged. This is a one-line change in the rule but reaches every caller of `isCreator`/`isClaimant`/`isProposer`, plus `reschedule.ts`'s own previously-duplicated copy of the same logic (now deleted in favour of calling the shared functions) and the raw SQL "Your requests" query, which needed `ownership.ts#ownerMatchSql` so it can't drift from the predicate functions.

The same review raised a second, related gap: creating a page or sending a request never required being signed in at all, so an anonymous visitor's device cookie was itself a kind of permanent, un-revocable credential by construction. `POST /moveouts` and `POST /m/:id/apply` now require a live session, redirecting an anonymous attempt to `/login?next=...` (a safe, same-site path only — `src/session.ts#safeNextPath` rejects anything else) rather than silently proceeding or returning a bare 403. Registering or logging in still offers to link a browser's own pre-existing, not-yet-claimed pages or requests (the legacy case this requirement doesn't remove), but that link is now the only way new anonymous data could ever exist going forward, and it's one-directional: claimed data can never be reassigned to a different account, and the original device loses access the moment it's claimed.

`spec/permission-regression.test.ts` adds ten scenarios directly reproducing that round's acceptance criteria — logout-then-replay, replaying a dead session alongside a live device cookie, switching accounts on one browser, the cross-device positive case still working, anonymous writes creating nothing, legacy-claim compatibility, duplicate/concurrent claim safety, and post-logout re-fetch rejection. Every one of them failed under the pre-fix `matchesOwner`-less OR logic (confirmed by temporarily reverting `src/ownership.ts` and re-running the suite) and passed after.

## Four more vulnerabilities found by independent review

A second review pass (reproduced with Codex, against a running server) found four further gaps the first fix's own OR-removal didn't close:

1. **Anonymous writes to unbound legacy data.** `isCreator`/`isClaimant` correctly recognise an unbound page by device id alone (needed so old data can still be found and claimed), but several write routes — add item/photo, add timeslot, change visibility, withdraw, confirm/cancel/complete, departure, change timeslot, every reschedule action — treated that recognition as sufficient authorization, with no separate "is this request signed in at all" gate. Reproduced directly against a real pre-accounts-shaped database row: a POST with only the matching `device` cookie created a real item. Fixed with one new gate, `src/session.ts#requireSignedIn(c, fallback)`, called first in every one of those routes, before any ownership check and before touching the database or an upload.
2. **A stale open tab kept showing private content after logout elsewhere.** `src/public/live.js#resync` treated a 401/403 response identically to a dropped network connection — "Could not sync — retrying," forever, while the DOM still showed the confirmed pickup address or management controls from before access was lost. Fixed by branching on response status: a 401/403 now stops the SSE connection and hard-navigates to the same URL, replacing the stale DOM with the server's own rejected-request view, rather than retrying something retrying can never fix.
3. **Cross-device duplicate applications.** `applications_one_active_per_device` scoped the one-active-request rule by device id, so the same account signed into two devices could hold two independently-valid active applications for one item — each device had its own id the index never connected. Fixed with a new index, `applications_one_active_per_identity`, scoped by `COALESCE(claimer_account_id, claimer_device_id)` — the same account-replaces-device rule as every other check in this app, now also enforced in the schema for this invariant. A dedup migration (`dedupeDuplicateAccountApplications`, guarded by `schema_migrations`) resolves any pre-existing violation first: never deletes a row, keeps the confirmed one if any (an item only ever has one) or the oldest pending one otherwise, and cancels every other one with a specific `cancel_reason` — the one the user explicitly required before building an index that real existing data might already violate.
4. **"My MoveOut" and stale tabs didn't update across devices on an account.** The SSE device bus (`src/live.ts`) was the only subscription "My MoveOut" ever used, so device A creating a page never woke device B's already-open home tab, even signed into the same account. Added a parallel account-scoped bus (`notifyAccount`/`onAccountChange`); every write that changes what an account's own list shows now notifies it, and `GET /events`/`GET /m/:id/events` both subscribe by account (resolved from the live session) as well as device. `POST /logout` also notifies immediately, which is what makes a sibling tab's resync (point 2 above) fire within about a second instead of waiting for an unrelated event.

Regression coverage: `spec/permission-regression.test.ts` scenarios 1 and 10 were corrected to the real expected behaviour (302-to-login before a 404, and a same-account second device correctly rejected rather than treated as independent) rather than encoding the bugs as "existing rules." `spec/migration.test.ts` gained two tests against a real pre-accounts legacy page, confirming the anonymous-write gate rejects it before and the device can still manage it normally after registering. `spec/duplicate-application-migration.test.ts` is new, seeding the exact pre-fix duplicate shape and confirming the migration resolves it, the new index exists and is enforced, and a second migration run changes nothing further. Every one of these failed against the pre-fix code (confirmed by stashing the fix commits' source changes and re-running) and passes after.

## Two more crashes in the account-scoped applications machinery

A third review pass found two crashes in the very fix that closed the duplicate-application gap above:

1. **The server wouldn't restart.** `src/db.ts`'s first, unconditional `db.exec(...)` block (plain table creation, run on every boot) also unconditionally recreated `applications_one_active_per_device` — the OLD, device-scoped index — even on a database where the later one-time migration had already replaced it with `applications_one_active_per_identity`. Reproduced for real: one browser applies as account A, logs out, applies as account B for the same item (two independently-valid applications under the current rule), then the server is stopped and restarted against that same `DATA_DIR` — it crashed on boot with `UNIQUE constraint failed`, because the unconditional block ran before the migration that would have dropped the old index ever got a chance to. Fixed by moving the old index's creation entirely inside the one-time migration that replaces it, so it's never recreated on a database already past it — see the new `spec/restart-after-account-scoped-applications.test.ts`, which drives real HTTP traffic to build this exact data shape and does a real stop/restart against the same directory (a hand-seeded fixture can't catch a startup-ORDER bug; this had to be a real two-boot test).
2. **Correct-password login 500'd.** `claimAnonymousDataForAccount` ran every one of a device's unclaimed applications' claims inside one shared transaction. If the signing-in account already had its own active request for an item this device also had an unclaimed request for, that one row's `applications_one_active_per_identity` violation threw out of the ENTIRE transaction — a correct password got a 500 and no session, for a reason that had nothing to do with whether the credentials were right. Fixed by isolating each application's (and reschedule proposal's) claim in its own SQL SAVEPOINT (`claimRowsOneAtATime`, `src/auth.ts`): a conflicting row rolls back to exactly its pre-claim state — untouched, still fully owned and manageable by the original anonymous device — without aborting any other row's claim or the session being created. The confirmation page (`accountClaimedView`) names the conflicting item directly with a working link, rather than a bare count or a vague "something didn't link" — the real path forward is to cancel one of the two duplicate requests and sign in again.

Both were reproduced for real before fixing: the restart bug by actually stopping and restarting a server process against data it had just created, the login bug by inserting a genuine unbound application row (not a mocked constraint error) that collides with an account's real existing one, then logging in with the correct password and observing the 500. `spec/claim-conflict.test.ts` covers ten scenarios: correct-password success despite a conflict, wrong-password still fully rejected, a confirmed booking never touched by a claim conflict, one browser with a claimable page plus both a conflicting and non-conflicting application resolving correctly in a single login with no half-completed state, and post-conflict logout still correctly revoking access. All ten failed against the pre-fix code (confirmed by stashing the fix and re-running) and pass after. Neither fix weakens `applications_one_active_per_identity` itself — it's still fully enforced; only the migration order and the claim pass's failure isolation changed.

## Verification and remaining evidence

`pnpm typecheck`, `pnpm test` (88 tests, up from 65), and `pnpm check:evidence` pass against a locally started server. Five browser scripts report 100% against a fresh server, each run at both 1920×1080 and 390×844: `scripts/browser-verify-accounts.mjs` (44 checks — login-gated publish/apply, cross-device management, cross-account isolation, logout/stale-cookie rejection, a genuinely-left-open tab clearing its private content on a sibling tab's logout, cross-device duplicate-apply rejection, cross-device live "My MoveOut" sync), `scripts/browser-verify-claim-conflict.mjs` (24 checks, new — correct-password login succeeding past a real rendered conflict notice with a working link, resolving it by cancelling the duplicate, and a wrong password still getting nothing), `scripts/browser-verify-pickup-card.mjs` (16 checks), `scripts/browser-verify.mjs` (34 checks), and `scripts/browse-verify.mjs` (10 checks).

Migration safety was verified on an isolated copy, not the live database: the OLD (pre-this-round) code was run in a separate git worktree to produce a real database with the exact crash-triggering shape (two accounts, one device, same item, from real HTTP traffic), that directory was copied as a backup, and the CURRENT code was run against the working copy — it migrated cleanly, both applications and their account ownership survived completely unchanged (neither cancelled, since they're genuinely different accounts, not duplicates), the old index was gone, and the new one was in place and enforced. Local persistence was separately verified end to end in its own isolated `DATA_DIR`: created a page, uploaded a real photo, applied, confirmed, set departure status, proposed a reschedule, registered an account, then killed and restarted the server process against the same data directory — every record, the account, its session row, and the photo's byte-identical content survived.

On the live Fly instance, this round's own clearly-labelled test data (`ZZZ-TEST-...` titles and emails) was used to verify both fixes in production without touching any other user's data or running the crash-reproducing scenario against the live database: an anonymous write attempt was confirmed redirected to login rather than silently allowed; two devices signed into the same account applying for the same item got the same account-scoped rejection a real duplicate-apply gets. The restart crash and the login-conflict 500 were NOT reproduced or fixed by directly manipulating the production database — that reproduction only ever happened in local/isolated copies, per the instruction not to inject dangerous legacy data into production; production itself was never in the broken state this round's fixes address, so there's nothing on the live volume for either fix to migrate.
