# Process overview

MoveOut coordinates student move-out handovers, now as a public discovery pool rather than only a link-shared tool. This account covers the project through this product-direction change: selection, agent direction, implementation, corrections and current evidence. It was written with agent assistance; the instructions and choices described are mine, and the verification below was executed by agents, not through a documented personal or classroom trial unless stated otherwise.

## Choosing the problem, the stack, and early bugs (Crits 7-9)

Student move-out handovers gave an earlier, vaguer idea a deadline and an observable outcome: whether someone actually collected an item, not just expressed interest. The brief limited MoveOut to free collection, pickup windows, one confirmed recipient per item, cancellation and completed handovers, with exact addresses hidden from unconfirmed recipients ([ab091d7](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/ab091d7c22f21d30ab02b9fca04817a2d30bdc6a)). ANU's [Give It Forward project](https://mccuskerinstitute.anu.edu.au/project/give-it-forward-circular-giving-in-residential-halls/) grounds the problem without proving scheduling causes the waste; [Robin Sloan](https://www.robinsloan.com/notes/home-cooked-app/) and [Aurora Harley](https://www.nngroup.com/articles/visibility-system-status/) argued for small-group scope and clear status feedback at the time — Crit 11 revisits that scope decision below.

Node 24 + Hono + SQLite ([9cda16a](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/9cda16a3293dbdca1ff3136df34d8ee65a4c18f0)) needs no separate database service and serves forms that work without JavaScript. My workflow separates implementation from review throughout: Claude makes the change, Codex checks it against the brief's actual behaviour, I feed findings back as concrete fixes. Crit 9 added real-time updates that preserve a person's unfinished form when someone else changes shared state ([a0f969a](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/a0f969a), [ADR 002](docs/decisions/002-live-updates-preserve-input.md)); review found several browser bugs and one real database bug (confirming an already-cancelled application could reserve the item before noticing the application update changed nothing — [ceb556a](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/ceb556a)). Crit 10 added the server-side business log ([ADR 003](docs/decisions/003-business-logging.md)) and re-verified the identity/permission model that this crit builds directly on.

## Crit 11: from link-sharing to a public browse pool

The direction for this round is an explicit, authorised change to the product itself, not an implementation detail: MoveOut's home page becomes Browse, a public pool of items across every mover who opts in, with search, category filtering and sort — while unlisted, link-only pages (the whole product through Crit 10) stay fully supported. CLAUDE.md's "out of scope" list previously named "a cross-page marketplace"; that line is now explicitly superseded there, with the narrower scope (browse/search/filter/sort, not ratings, chat or recommendations) restated in its place.

I had Claude read the existing identity, ownership and real-time code before changing anything (`src/session.ts`, `src/ownership.ts`, `src/live.ts`, every route and view) rather than guess at what it already did, since a public pool changes the actual privacy boundary — a page reachable only by a link someone chose to share becomes reachable by a stranger typing words into a search box, which is not a change to make assuming the old rules still apply unexamined. [ADR 004](docs/decisions/004-public-browse-visibility.md) records the resulting design: a page gets an explicit, creator-only, server-validated `public`/`unlisted` flag; the pool query (`src/ownership.ts#listBrowseItems`) is one parameterised SQL statement scoped to `visibility = 'public' AND status = 'open' AND deadline_at > now`, never a broader fetch filtered client-side or in application code after the row's already left the database.

The schema migration adding `visibility` and `category` ([be9dd27](https://github.com/comp4020-agentic-coding-studio/comp4020-final-tavewang/commit/be9dd27)) is additive and re-runnable: no `DROP`, no rebuild, guarded by inspecting the live schema (`hasColumn`) since SQLite's `ALTER TABLE` has no `IF NOT EXISTS`. Every move-out page that existed before this flag defaults to `unlisted`, not `public` — a deliberate choice verified by a test that seeds a database shaped exactly like the pre-Crit-11 schema and checks the migrated result, rather than trusting the migration code's own comments. Items default to the `"Other"` category for the same reason: guessing an existing item's category from its name would be putting words in its original poster's mouth.

Three real reliability gaps surfaced while building this, found by re-reading routes that the new pool-visibility writes now had to call into: `POST /applications/:id/timeslot`'s guarded `UPDATE` never checked its own `changes` count, so a race against a creator's confirm could leave the database untouched while the route still returned success and logged it as one; the apply route's duplicate-request handler treated every thrown database error as "you already applied," which would mislabel a genuine server fault as a routine conflict; and a test named "two applicants with the same nickname... stay isolated" only ever had one of them actually use that nickname, dodging a name-based test helper rather than proving the claim. All three are fixed with their own regression tests (`spec/moveout.test.ts`, `spec/browse.test.ts`) — the nickname test now has both devices literally apply as "Sam" to the same item, with each reading its own application id off its own view rather than a shared-name lookup.

The pool's real-time behaviour follows the same pattern Crit 9 established rather than inventing a parallel one: a third notify bus (`notifyPublicPool`) carries the same content-free "something changed" signal, and the existing client (`src/public/live.js`) re-fetches whatever URL (including its current `?q=`/`?category=`/`?sort=`) the visitor already had open — no Browse-specific reconciliation code, so an in-progress search draft is protected by the same `isProtected` check that already protects any other form.

For the visual direction, I checked this environment for an installed design skill and an image-generation tool before starting; neither was available (no `frontend-design`-style skill in the local skill set, no callable image-generation tool). I'm recording that as a real gap rather than claiming a substitute satisfies it: the empty-state and no-photo illustrations here are hand-authored inline SVG, not output from a generative art tool, and that distinction matters for anyone checking this claim.

## Final-project pickup upgrade: full arrangement card, travel status, mutual reschedule

This round answers a gap the deployed app actually had: a confirmed claimant's own "Your requests" card never showed the pickup time it had just been confirmed against, and once confirmed there was no way for either side to move the appointment without cancelling and reapplying from scratch, or for the claimant to tell the mover they were on their way. The three features below are additive to the existing confirm/cancel/complete lifecycle, not a replacement for it — explicitly out of scope: email notification (discussed, deferred — no external mail service configured in this environment), chat, payments, cross-device login, automatic waitlist promotion.

I had the agent read `CLAUDE.md`, `src/ownership.ts`, `src/routes/applications.ts`, `src/db.ts`, and `src/public/live.js` before writing anything, the same discipline as Crit 11's pool work — the existing guarded-`UPDATE` concurrency pattern, the two-status-column separation (`items.status` / `applications.status`), and the SSE "something changed, re-fetch" bus all had to be extended, not reinvented, for a reschedule proposal to behave consistently with everything already in the app.

**Schema**: one additive column (`applications.departure_status`, default `'not_departed'`) and one new table (`reschedule_proposals`, a proposer, a target timeslot, a reason, and a status machine of `pending → accepted | declined | withdrawn | invalidated`) — both guarded the same way as Crit 11's migrations (`hasColumn`/live-schema inspection, no `DROP`, re-runnable). `spec/migration.test.ts` now also seeds a database shaped like the pre-this-round schema and checks the legacy application migrates to `not_departed` with its history untouched.

**Departure status** (`POST /applications/:id/departure`): claimant-only, confirmed-only, free movement between the three values (not a one-way ratchet — correcting a misclick is allowed), blocked the instant the booking is cancelled or completed. Rendered as three plain buttons rather than a `<select>`, specifically because `src/public/live.js`'s `isProtected()` treats any non-default `<select>` as a draft in progress and would have permanently frozen that card's live sync the moment someone picked "Arrived".

**Mutual reschedule** (`POST /applications/:id/reschedule`, `/reschedule/:id/{accept,decline,withdraw}`): either party can propose a different timeslot already on the same page (no second timeslot system), with a ≤200-character reason; the other party accepts or declines, the proposer can withdraw; a proposer can't accept their own proposal; at most one pending proposal per application (a second partial-unique index, same pattern as `applications_one_active_per_device`); accepting re-validates the proposal, the application's still-confirmed status, and the target slot's still-future start all inside one transaction, moves the timeslot, and resets departure status to `not_departed` — all four, or none, same discipline as the existing confirm transaction's two-guard pattern. Cancelling or completing the booking invalidates any pending proposal outright, so a stale "Accept" button can never resurrect a booking that no longer exists.

**A real bug found by actually running the two-browser verification, not just the automated tests**: my first version of `syncPickupCard` (`src/public/live.js`) always replaced the confirmed-pickup card wholesale on every SSE sync, including its own open "Propose a different pickup time" sub-form — so typing a reason into that field and having any unrelated event on the page fire (another timeslot add, a departure-status change) would silently wipe the input before submit. Playwright's two-context run against the real server caught this reliably where the automated spec suite's `fetch`-based tests could not (they never render a DOM to lose a draft from). Fixed by making `syncPickupCard` defer to the same `isProtected()` check already governing every other draft on the page — see the comment at that function for why the surrounding, much larger application-card wrapper (`patchSafeBits`'s caller) isn't the right thing to check instead.

**Verification actually executed, not asserted**: `pnpm typecheck` and `pnpm test` (53 tests, up from 35 — 18 new, covering both-direction proposals, self-accept/third-party rejection, decline, withdraw, invalid-timeslot rejection on four different grounds, concurrent-propose and double-accept races, cancel-invalidates-pending, departure-status permission/terminal-state/non-ratchet rules, and that the new routes don't weaken existing location-privacy or one-confirmed-recipient guarantees) all pass. `pnpm check:evidence` passes. A real Playwright script (not a mock) drove two actual browser contexts (owner + claimant) against the running local server at both 1920×1080 and 390×844, through: create → two timeslots → one item → apply → confirm → claimant sees the full card **live, no reload** → departed → arrived, both observed live on the owner's open tab, without reload → mark picked up; and separately: confirm → claimant proposes a reschedule → owner sees the proposal **live** → owner accepts → claimant sees it resolve live with travel status reset → the claimant's own browser context (same device cookie, no in-memory state) reopened the page afresh and the confirmed arrangement was still correct, proving SQLite persistence rather than an in-page client cache. Not yet done at the time of this write-up: deployment of this round's changes to the live Fly instance, and a verification pass against that deployed URL specifically (the app has been exercised locally only).
